# Нова версия

1. `Directory.Build.props` – променете `<Version>`, например `1.0.1`.
2. `CHANGELOG.md` – добавете раздел `## 1.0.1 – дд.мм.гггг` най-отгоре. Този текст вижда потребителят в прозореца „Обновяване“.
3. Ако са променени правила за видовете сделки – обновете `Deal_Type.md` (номера на версията и раздел „Промени“).
4. `dotnet test`
5. Качете и маркирайте:

```
git add -A
git commit -m "Версия 1.0.1"
git tag v1.0.1
git push origin main v1.0.1
```

GitHub Actions (`.github/workflows/release.yml`) проверява, че маркерът и `<Version>` съвпадат, пуска тестовете, прави един `MicroinvestConvert.exe`, пакетира го като `MicroinvestConvert-1.0.1-win-x64.zip` и публикува версията с текста от `CHANGELOG.md`. Инсталираните програми я виждат при следващото си стартиране.

GitHub сам публикува контролната сума (SHA-256) на всеки файл; програмата не инсталира файл, който не съвпада с нея.

## Репетиция на обновяването

Преди версия, която променя самото обновяване – с две истински програми (отварят се прозорци):

```
dotnet publish src/MicroinvestConvert.App -p:PublishProfile=win-x64 -p:PublishDir=<папка1>\
dotnet publish src/MicroinvestConvert.App -p:PublishProfile=win-x64 -p:Version=9.9.9 -p:PublishDir=<папка2>\
$env:MICONVERT_OLD_EXE = "<папка1>\MicroinvestConvert.exe"
$env:MICONVERT_NEW_EXE = "<папка2>\MicroinvestConvert.exe"
dotnet test --filter UpdateRehearsal
```

Тестът пуска старата, подменя я, докато работи, пуска новата, проверява, че старата е запазена, и се връща към нея.

## Ако нещо се обърка

- Версия, публикувана по грешка: изтрийте я от страницата Releases – програмите ще виждат предишната като последна.
- Потребител с проблемна версия: „Обновяване → Предишна версия → Върни тази версия“.
- Ако хранилището стане частно, програмите вече няма да виждат версиите – обновяването чете публичните.
